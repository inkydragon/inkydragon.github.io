# 可复现数值正确性基础设施

> 状态：项目构想。三层职责已经初步确定；第一阶段只做整体架构和一个基础函数的 draft 规范案例。

## 一句话定位

给定一个版本化的实现合同、一个具体数值实现和一组实际环境配置，生成可复现、可审查、带覆盖边界的正确性与一致性证据。

项目面向数值算法的实现者和使用者。它不以长期维护某种语言的完整数学库为主要目标，也不承担数学算法知识库的全部职责。具体实现可以被 AI 重写、重构和替换；长期保留的核心资产是实现合同、测试框架、验证方法、环境 profile、失败案例和可复现报告。

## 背景动机

AI 使代码生成、语言迁移、重构和形式化证明草稿的成本持续下降。未来，按照要求生成一个 Lean4 算法、提取为 Rust、导出 C API 并用高精度库测试，可能不再是稀缺能力。

因此，项目的主要价值不应定义为：

- 实现了多少个函数；
- 手写了多少证明；
- 维护了多少行特定语言代码。

项目真正要解决的是：

- 具体实现是否满足明确合同；
- 不同语言、编译器、平台和优化选项会产生什么差异；
- 如何区分数学错误、实现错误、工具链错误和系统错误；
- 测试阈值放宽是否掩盖了算法退化；
- 在没有单一高精度 oracle 的算法中，如何组合多种证据；
- 部分验证结果如何被准确描述，而不是被笼统称为“正确”。

项目最终希望成为面向具体数值实现的验证工作台，而不是另一个普通数学库、算法百科或绝对性能排行榜。

## 与 Math Func Correctness Atlas 的关系

Math Func Correctness Atlas 与本项目位于不同的抽象层次。

Atlas 类似 DLMF 的增强版，面向算法研究者和开发者，主要回答：

> 一个数学函数有哪些表示、算法和理论性质？

Atlas 关注：

- 多项式、有理函数和其他表示；
- 系数构造；
- 逼近误差；
- 收敛性和条件数；
- 范围规约；
- 经典算法及其适用范围；
- 理论精度分析和算法取舍。

本项目面向算法实现者和使用者，主要回答：

> 这个具体算法、具体形式、具体系数和具体环境下的实现，是否真的满足它声称的要求？

两者的基本关系是：

```text
Math Func Correctness Atlas
  数学函数、算法表示和理论性质
              ↓
具体算法实例
  固定形式、系数、输入域和浮点配置
              ↓
本项目
  实现验证、误差证据、差异分析和使用决策
```

可以用一句话区分：

```text
Atlas：应该怎样实现？
本项目：这个实现真的做对了吗？
```

Atlas 可以提供算法和理论背景，本项目把其中的具体实例变成可验证的实现对象。本项目案例中发现的失败模式和工程约束，也可以反过来补充 Atlas 的算法分析。

## 总体承诺与证据边界

项目对用户的最高层承诺是：

> 对于明确的规范、实现、环境和测试条件，生成带证据边界的数值正确性与一致性报告。

项目不承诺判断任意实现是否普遍正确，也不承诺为所有高层算法提供单一高精度 oracle。任何结论都必须绑定到：

- 规范版本；
- 实现版本；
- 环境 profile；
- 输入域；
- 测试和证明方法；
- 已覆盖和未覆盖的假设。

三层结构如下：

```text
规范层
  ↓
精确舍入基础数学函数层
  ↓
需求驱动的可复现数值算法层
```

三层都可以使用 AI 驱动开发，但人工需要长期负责规范审查、验收标准、可信边界和项目方向。

## 第一层：实现合同规范层

### 职责

规范层负责定义：

- 实现合同；
- 测试要求；
- 证明要求；
- 结果报告要求；
- 版本和变更规则。

它回答：

> 一个具体实现要满足什么条件，才能声称符合该规范？

规范层可以使用 C23 等语言和浮点标准作为规范来源，借此限定基本语义和正确性要求。但它不负责维护具体编译器、CPU、FMA 或 SIMD 配置；这些属于第二层的实现环境 profile。

### 规范内容

对于基础数学函数，可以描述：

- 函数定义、定义域和返回类型；
- 特殊值、负零、无穷和 NaN；
- 奇点、极点和分支切割；
- 舍入模式和正确舍入要求；
- 溢出、下溢和次正规数行为；
- 异常标志和错误处理；
- 对称性、单调性和其他数学性质；
- 精度目标和误差界；
- 测试覆盖和证明要求。

对于具体数值算法，可以描述：

- 前置条件；
- 后置条件；
- 循环不变量；
- 算法属性；
- 收敛性或稳定性要求；
- 归约顺序和确定性要求；
- 边界测试；
- 经典工业验证算例；
- 允许的误差或结果等价关系。

数学函数的算法表示、系数构造、逼近和收敛性主要由 Atlas 提供参考；本项目规范层负责把选定实现转化为可验收合同。

### 文档和机器可读格式

Markdown 暂定为规范的主要载体，因为规范需要被人工阅读、讨论、审查和长期迭代。

第一阶段不讨论 Schema、如何形式化规范，或是否使用某种 DSL。这些内容作为后续工具化 TODO，等待更多外部标准和实际案例信息后再决定。

未来可以考虑由 Markdown 规范抽取机器可读内容：

```text
Markdown 规范
    ↓ AI 抽取
JSON 实例
    ↓ JSON Schema 校验
测试、报告、代码生成和工具集成
```

需要区分：

- Markdown：规范的主要叙述载体；
- JSON Schema：机器可读数据结构的约束；
- JSON：某个函数或算法的具体规范实例；
- 测试与报告：从规范派生的执行产物。

如果未来确实需要机器可读格式，再讨论 JSON Schema、JSON 实例以及现有符号计算语言或其他 DSL。当前不预先设计专用 DSL。

### 版本、人工审查和发布

规范需要长期迭代。当前只定义规范版本：

```text
规范版本：数学语义或验收要求发生变化
```

每次实质修改记录：

- 修改原因；
- 影响的函数或算法；
- 是否破坏既有实现；
- 是否需要重新生成测试；
- 哪些旧报告不再适用。

规范状态包括：

```text
draft：未经人工审查，只能用于讨论和实验
reviewed：已完成人工审查，等待发布
published：已固定版本，可用于正式符合性结论
```

未经审查的内容默认属于 `draft`。draft 规范可以生成实验结果、测试结果和问题清单，但不能生成正式符合性结论。

规范发布后保持不可变。发现错误或需要改变要求时，始终通过发布新版本修改，不在原版本上直接编辑。旧版本下的报告继续对旧规范有效，新版本不自动继承旧报告；受影响的实现需要重新验证。

AI 可以抽取 JSON、生成候选性质和检查内部一致性，但人工需要审查：

- 数学定义是否正确；
- 标准映射是否合理；
- 前置和后置条件是否过强或过弱；
- 是否把实现细节误写成数学要求；
- 版本变更是否改变了实际含义。

实现可以暴露规范遗漏，但不能自动决定规范内容。推荐流程是：

```text
实现或环境中的问题
  → 证据记录
  → 规范扩展提案
  → 人工审查
  → 新版本发布
  → 重新验证已有实现
```

AI 可以参与草案生成、测试和疑点整理，但不能自动完成规范审查、改变规范状态或发布版本。规范发布需要人工审查和明确的版本提交。

## 第二层：产品级基础函数验证层

### 职责

第二层面向产品级数学基础函数的验证，以及可复用的验证框架。通过验证的具体实现可以另行拆分为产品级数学库维护；本项目不永久绑定 Rust、C、Julia 或其他某一种实现，也不承诺直接维护所有语言实现。

它回答：

> 一个基础数学函数的具体实现，在声明支持的环境中，是否满足强度足够高的实现合同？

精确舍入 libm 是这一层的主要起点。Core-math f32 等已有实现可以作为第一个参考对象，但不是唯一真值，也不必成为项目永久维护的唯一代码。

### 产品级目标

在适用范围内，第二层可以追求：

- 在声明支持的环境 profile 集合内实现跨 profile 的正确舍入；
- 明确的浮点语义；
- 明确的支持定义域；
- 独立 oracle；
- 完整的边界和最坏案例测试；
- 可审查的证明或误差证据；
- 稳定的验证接口和报告格式。

如果只能在单一平台、统一环境或部分定义域内完成验证，通常更适合作为第三层案例，而不是直接声称达到第二层的产品级目标。第二层产生的具体实现可以另行拆分为产品级数学库维护，但本项目本身不承诺维护所有语言实现。

### 实现与环境 profile

具体实现属于第二层的讨论和验证对象。每个实现需要配对环境 profile，记录例如：

- 语言和版本；
- 编译器、LLVM 和版本；
- CPU 架构和可用指令集；
- 编译选项和优化级别；
- FMA 和 SIMD 是否启用；
- 舍入模式和浮点环境；
- 线程和运行时设置；
- 依赖版本和构建信息。

环境 profile 可以先按语言、编译器和平台分别整理。实践足够后，再决定哪些约束可以提升为公共规范，哪些必须保留为环境特定要求。

### 分级的 bit-for-bit 目标

第二层可以对精确舍入 libm 采用分级能力声明：

```text
Level 1：有限输入和有限结果的正确舍入及 bit pattern
Level 2：特殊值、负零、无穷和次正规数行为
Level 3：舍入模式、异常标志、NaN 传播和浮点环境
```

不同硬件和编译器对 Level 2、Level 3 的支持可能不同，因此每个 profile 必须声明：

- 达到的等级；
- 不支持的特性；
- 已知差异；
- 验证证据。

这里的等级只是实现能力和环境 profile 的当前边界示例，不是第一层规范的分级。第一层规范应尽可能完整地限定什么是正确实现；第二层报告不同 profile 实际能够验证到什么程度。

### 重要资产

- 独立高精度 oracle；
- 正确舍入边界测试；
- 特殊值和异常行为测试；
- 性质测试和 metamorphic testing；
- 已知最坏案例；
- 历史失败输入；
- 形式化验证接口；
- 环境 profile；
- 可复现精度报告。

测试系统不能主要从被测实现中派生，否则 AI 重写实现时可能同时继承原实现的错误假设。

### AI 驱动的实现流程

AI 可以负责：

- 将参考算法重写为其他语言；
- 生成多个实现候选；
- 生成属性测试和边界测试；
- 生成 Lean 定义、定理和证明草稿；
- 分析失败输入；
- 自动修复和重构实现；
- 生成跨平台报告。

验证框架负责：

- 固定规范版本；
- 运行独立 oracle；
- 校验测试覆盖范围；
- 记录环境 profile；
- 判断是否达到声明的验证等级；
- 保存失败案例和修复历史。

具体实现通过验证后，可以拆分为独立的产品级库维护；但实现本身不是项目最核心的长期资产。

## 第三层：需求驱动的数值算法试验场

### 职责

第三层完全由需求和案例驱动，用于说明验证流程在真实数值算法上的可行性，并探索工业界真正关心的目标。

它不是第二层的低质量版本，也不是预先规划好的完整数值算法库。它回答：

> 对于一个具体生产案例，我们究竟能够定义、测量和保证哪些结果性质？

第三层可以研究：

- 一致性；
- 运行结果的可复现性；
- 确定性；
- 数值稳定性；
- 误差和残差；
- 工具链、编译器和平台差异。

这些目标不是每个案例都必须满足的统一要求。实际能够做到什么、哪个目标更重要，都需要通过案例探索。

### 结果优先，构建复现只是辅助工具

第三层主要关注运行结果，而不是构建产物 hash。

可复现构建可以帮助固定源码、依赖和工具链，缩小差异来源；但它不是第三层本身的目标。相同二进制也可能因为线程调度、硬件状态或未定义行为产生不同运行结果；不同二进制也可能满足同一个数值合同。

因此需要区分：

```text
构建可复现性：辅助固定实验条件
运行结果验证：第三层的主要目标
数值合同：判断结果是否合格的依据
```

### 案例合同

每个案例单独定义结果等价关系，而不是由第三层统一规定“所有结果必须 bit-for-bit 相同”。可能的结果合同包括：

- bit-for-bit 相同；
- ULP 距离受限；
- 绝对误差受限；
- 相对误差受限；
- 残差受限；
- 满足数学不变量；
- 满足收敛或稳定性条件。

一个案例章程可以包括：

```text
案例对象
目标函数或算法
真实生产背景
候选环境
已知影响因素
待研究的结果性质
结果等价关系
候选验证方法
当前能够达到的目标
已知无法保证的目标
最终结论
```

第三层一开始可以只有研究问题，完成研究后再把确认过的内容提炼为正式合同。无法确认的部分应记录为“证据不足”，而不是强行归入正确或错误。

### 从简单 kernel 逐步扩展

第三层应逐步开始：

```text
固定顺序求和
  → dot product
  → 固定规模 GEMM
  → 单线程 BLAS GEMM
  → SIMD、并行和多平台 GEMM
  → 更复杂的生产算法
```

也可以把尚未达到第二层强合同的特殊函数放入第三层。例如一个特殊函数可能由范围规约、多项式求值、多个 libm 调用和求和组成。即使其中的 `sin`、`exp` 等基础函数已经通过第二层验证，整体函数仍需单独研究：

- 系数表示误差；
- 多个调用的误差累积；
- 求和顺序；
- cancellation；
- 分支选择；
- 溢出和下溢传播。

如果后来能够为该实现建立跨平台、完整定义域和强度足够高的验证合同，它才可能晋升为第二层的产品级对象。

### 生产库案例

OpenBLAS 可以作为第三层的生产导向案例，但应从具体函数和固定条件开始，而不是直接声称验证 BLAS：

- 函数和数据类型；
- 矩阵布局和转置选项；
- 维度范围；
- 线程数；
- CPU 特性；
- 编译器和优化选项；
- FMA、SIMD 和归约策略；
- 结果比较方式。

如果新实现与现有库不一致，只能说明至少一个实现、环境或比较假设存在问题。需要结合 oracle、数学不变量、误差界、最小化反例和独立编译器复现来判断根因。

## Oracle 的分层设计

对于基础函数，高精度浮点库可以提供接近直接的 oracle；对于高层数值算法，通常不存在类似 GMP 的万能 oracle。因此项目需要建设可组合的 oracle hierarchy：

```text
精确整数或有理数
    ↓
高精度浮点
    ↓
区间或区间向量
    ↓
形式化参考算法
    ↓
数学不变量
    ↓
metamorphic relation
    ↓
独立实现共识
    ↓
误差、残差和收敛界
```

不同问题使用不同证据组合：

- `sin`：高精度或正确舍入 oracle；
- `gemm`：小规模高精度结果、残差和误差界；
- 线性求解器：残差、条件数和已知解；
- 迭代算法：收敛性和不变量；
- 统计算法：分布性质和 metamorphic testing；
- 更高层系统：可验证子组件、约束、回归案例和多种独立证据。

项目不承诺一个万能 oracle，而是为不同类型的算法提供分层、可组合、带证据边界的 oracle。

## 超越 ULP 阈值

长期只能依赖 ULP 阈值，会掩盖不同层面的问题。更新算法时，直接放大阈值可能隐藏：

- 算法精度退化；
- 某个输入区域失去稳定性；
- 特殊值行为改变；
- 归约顺序变化；
- 编译器优化差异；
- 测试本身过度依赖旧实现。

测试报告应该记录：

- 当前规范版本；
- 适用的前置条件；
- 结果比较方式；
- 误差分布，而不只有最大 ULP；
- 失败输入所在区域；
- 与历史版本的比较；
- 是否可能是工具链或平台问题；
- 当前证据尚未覆盖的部分。

允许放宽阈值时，应记录放宽原因、影响区域和新的误差预算，而不是只修改一个数字直到测试重新通过。

## 与 y-cruncher 类项目的类比

y-cruncher 的启发不只是“计算高精度的 π”，而是严格结果目标可以使系统错误无法被近似误差掩盖。因此，一个数学计算程序可以成为计算机集群、存储、网络、内存、处理器和工具链的端到端测试案例。

本项目希望逐步形成类似能力：

```text
严格规范与参考结果
    ↓
数值计算任务
    ↓
中间结果和最终结果校验
    ↓
跨平台、跨工具链和跨系统比较
    ↓
异常检测与根因定位
```

严格 oracle 能够发现异常，但不能单独定位异常。要区分算法、编译器、硬件、磁盘或网络错误，还需要校验和、冗余计算、独立实现、分阶段 checkpoint 和最小化重现案例。

## 第一阶段建议

第一阶段只涉及第一层，甚至主要是整体架构和一个规范案例，不进入第三层，也不要求完成第二层实现框架。

第一阶段的交付物是：

1. 明确三层架构和职责边界；
2. 整理 C23、IEEE 及其他相关标准的适用范围调查 TODO；
3. 以 Markdown 写出 `f32 sqrt` 的 draft 规范案例；
4. 包含有限输入、特殊值和非法数学输入的正确性要求；
5. 记录规范的人工审查、reviewed 和 published 流程；
6. 记录未来第二层验证框架需要接入的证据类型和环境 profile 概念。

第一阶段暂不要求：

- 完成 `sqrt` 的具体实现；
- 完成第二层验证框架；
- 完成形式化证明；
- 设计 JSON Schema 或其他机器可读格式；
- 选择或设计 DSL；
- 接入第三层数值 kernel、BLAS 或其他生产库。

`f32 sqrt` 当前是第一案例候选。标准范围调查完成前，规范保持 `draft`，不能产生正式符合性结论。

## 非目标

项目目前不承诺：

- 维护完整的生产级数学函数库；
- 替代 Core-math、OpenBLAS、BLAS 或 scipy；
- 为所有数值算法提供形式化证明；
- 为所有高层算法提供单一高精度 oracle；
- 立即支持所有语言和平台；
- 为第三层预先制定统一的结果等价标准；
- 建立一个覆盖全部数值计算领域的专用 DSL；
- 用一个绝对排名判断哪个库最好。

## 当前共识与待决策问题

### 当前共识

- 项目最高层承诺是生成带证据边界的实现正确性和一致性报告。
- Atlas 是数学和算法参考层，本项目是实现验证和使用决策层。
- 规范层只负责实现合同、测试要求、证明要求和版本化，不重新承担算法百科职责。
- 实现和环境 profile 属于第二层的验证对象；实现可以反哺规范，但规范变更必须人工审查和版本化。
- 第二层是产品级强合同方向，精确舍入和跨平台 bit-for-bit 是重要目标。
- 产品级数学库是第二层验证可以产出的独立成果，不是本项目第二层必须直接维护的对象。
- 第二层的跨平台目标限定在声明支持的环境 profile 集合内。
- 第二层可以有分级验证等级，不要求所有平台支持全部特殊值和浮点环境特性。
- 第一层规范本身不分验证等级，而是尽可能完整地限定正确实现；等级描述实现和 profile 的实际证据能力。
- 第三层完全需求驱动、案例驱动，是验证流程和规范发现的试验场。
- 第三层关注运行结果；构建可复现性只是辅助诊断工具。
- 第三层的结果等价关系由案例单独定义，不统一要求 bit-for-bit。
- 第一阶段只涉及整体架构和第一层的 `f32 sqrt` draft 案例，不进入第三层。
- 未经人工审查的内容默认是 `draft`，只有 published 版本可以用于正式符合性结论。
- 已发布规范不可原地修改，错误和决策变化始终通过新版本修订；旧报告继续对旧规范有效。
- 代码可以被 AI 替换，框架、规范、证据、失败案例和报告格式是主要长期资产。

- 哪些证据等级可以支持产品级发布。
